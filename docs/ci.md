## Gates（harness）

單一事實來源是 `Taskfile.yml`，Claude Code hooks、lefthook、CI 都只是呼叫它：

- `scripts/affected.sh`：由 `go.work` 算出被改動的 module，並展開反向依賴（改 kernel → 全部；改 ordering → ordering + apps/rpc）
- `scripts/ci-changes.sh`：由改動的路徑算出 ci.yml 每個 job 的 `run_<job>` 旗標（`affected` job 的 outputs，其餘 job 都 `if:` 它）；本機 `scripts/ci-changes.sh` 看這支 branch 會跑哪些，`CI_ALL=1`（全部 true）是 main 與 dispatch 的行為；對照表由 `scripts/test.sh`（`task scripts-test`）釘住：每條規則有只改單一路徑的案例，正反兩向都測，`ci.yml` 的每個旗標都宣告為 `affected` 的 output 且只被一個 job 的 `if:` 讀取，本檔列出每個 job 的名字。helm-kind、helm-kind-payment、helm-kind-keda、helm-kind-target、k6-auth、k6-wire 是各自獨立的 job（不用動態 matrix），略過時留下 skipped 的 check。k6-auth 內部是**靜態** matrix（`shard: ["1/3","2/3","3/3"]`，`K6_AUTH_SHARD=<i>/<n>`：`K6_AUTH_LIST=1 tests/k6/auth-matrix.sh` 列出的 27 個 cell 依序號 `(p-1) % n == i-1` 分組），每個 leg 一台 runner、一個自己的 Postgres service，所以 DB、worker consumer group、outbox backlog、port、catalog-rpc 都不跨組共用，隔離靠分開的 runner 而不是清理（#448）；`scripts/test.sh` 釘住 shard 為 1/n…n/n、各組聯集等於全集且無重複，`auth-matrix.sh` 對不存在的 cell 名稱報錯（不再靜默什麼都沒跑）。本機 `task k6-auth-matrix` 與 `task k6-auth-matrix -- <cell…>` 不變維護規則：`scripts/test.sh` 新增讀取或執行 `scripts/` 以外的檔案時，要同步把該路徑加進 `ci-changes.sh` 的 `scripts_src`，並在 `test.sh` 補只改該路徑的 sole-path 案例，否則只改那個檔案的 PR 不會跑 scripts-test
- `scripts/suite-guard.sh`（#307）：`scripts/test.sh` 一開始就用它重新執行自己——套件跑在**自己的 process group**，結束時（正常、有案例失敗、被 INT／TERM 打斷都算）檢查該 group 還有沒有活著的 process（stub server 等背景 fixture）：有就印出數量與指令、先 TERM 再 KILL 並等它們結束，並讓套件失敗（原本是 0 就改成 1；原本就失敗則保留原退出碼）。收到 INT／TERM 時先對 group 送 TERM，套件若忽略它就在 `SUITE_GUARD_GRACE`（預設 5）秒後對整個 group 送 KILL，守衛不會被不肯結束的套件拖住；只動自己建立的 group，不掃描也不殺別的行程；套件自己的 EXIT trap 管不到沒登記的 fixture、`set -e` 提前中止、SIGKILL，這層才是保證。守衛本身由 `test.sh` 的 `guard:` 案例釘住（假套件留下背景行程：正常／失敗／忽略 TERM，以及 INT／TERM 中斷，另外確認 group 外的行程不受影響）。
- `scripts/merge-ready.sh <pr>`（`task merge-ready -- <pr>`）：**merge 前必跑**。`pull_request` run 驗的是 `refs/pull/N/merge`——PR head 合進「run 開始當下的 main」；main 之後前進，這顆綠燈就不再是 main + 這個 PR 的結果（#187 改了 `NewCreateOrder` 簽章、#188 新測試還用舊簽章：各自綠、git 無衝突、合起來編譯失敗）。腳本取該 head 最新的 ci.yml run、找出它的 merge commit，比對 merge commit 的 base parent 與 main 現在的 HEAD、head parent 與 PR head；並確認 run 已完成、check 齊全且無 pending / fail / cancel。輸出 main / merge / base / head 四個 SHA 與 check 數。exit 0 可合、1 check 未完成或失敗、2 stale（不可合，先重驗）、3 用法錯
  - **stale 的重驗**：`task merge-ready -- <pr> --revalidate` 派送 `.github/workflows/merge-tree.yml`（`workflow_dispatch`，input 為 pr / head / main SHA），用 `scripts/merge-tree-check.sh` 在記憶體裡 `git merge-tree` 合 main + head、匯出 tree、對每個 go.work module 跑 `go vet ./...`（含測試編譯）；workflow 第一步（任何 setup / 以 base checkout 之前）用 `scripts/merge-tree-inputs.sh` 驗輸入（pr 純數字、head / base 為 40 位小寫 hex，後綴或空白一律拒絕），checkout 後再 assert `HEAD == base`，所以成功 run 的標題 `pr= head= base=` 就是實際 build 的 SHA；下一次 merge-ready 以**完整等值**比對標題（不是子字串）與 completed / success，只放行「恰好是現在的 main 與 head」的成功 run。**不要用 `gh run rerun`**：實測 rerun 沿用原本的 merge commit（#188 在 main 前進後 rerun，attempt 2 仍是同一個 merge SHA、base 仍是舊 main），等於重跑同一棵 stale tree；也**不要 update branch**：PR head 一變就要重審。`merge-tree.yml` 要在 default branch 上才能派送
  - 本機也能直接跑：`scripts/merge-tree-check.sh origin/main origin/<branch>`（git >= 2.38；0 可編譯、1 不能編譯、2 git 文字衝突）
  - `scripts/test.sh` 釘住它：stub 掉 `gh` 測 fresh / stale / head 不符 / pending / fail / 無 run / `--revalidate` 不用 rerun；另用兩條本機分支（一條改 constructor、一條新增舊呼叫）證明「git 無衝突、各自可編譯、合成 tree 編譯失敗」會被抓到
- `scripts/cover-gate.sh`：所有 `*/domain/*` package 必須 100% 覆蓋
- Go cache（`.github/actions/setup`，#450）：兩種 cache，**只有 default branch 上的 `push` 與 `workflow_dispatch` 會寫**（`.github/actions/setup/plan.sh` 是唯一的判斷處，每個 cache step 只讀它的輸出，且每個會 save 的 step 都有一個 `if:` 剛好相反的 `actions/cache/restore` 雙胞胎；`scripts/test.sh` 對 plan.sh 跑 trigger 表、把兩個 action 每對 rw／ro 的 `if:` 對 7 種 event × 5 種 ref × 各 scope 逐格求值、做結構檢查，並對 plan.sh／go-mod-download.sh／count_lines 用 PATH 注入的 `date`／`sleep`／`grep` 做 fault injection，gate 本身不吞退出碼；#461）。GitHub 對其他解析到 default branch 的 trigger（`workflow_run`、`pull_request_target`、`issue_comment`……）只給 read-only，pull request 寫的是 `refs/pull/N/merge`，只會把 main 要用的項目擠出去。以前每個 job／matrix 項目各存一份 mod＋build cache，一個 PR 一 miss 就存整組：2026-11-04 兩支 PR 讓 repo cache 到 14.8GB（上限 10GB），main 的 23 份被擠光，之後每個 job 冷編譯（870–926 次 compile、75–116 秒），冷的 module 下載也撞上 proxy 的 HTTP/2 `INTERNAL_ERROR`。現在：
  - **module cache**：全 repo 一份 `gomod-<os>-<go.sum hash>`，只放 `$GOMODCACHE/cache/download`（zip，約 0.26GB；module 在第一次用到時才解開，apps/rpc 約 2 秒，比多還原 400MB 的展開樹便宜）。module 版本不可變，同一份 go.sum 永遠有效，go.sum 變了才換一份，`restore-keys` 退回上一份。非 exact hit 時（main 上 go.sum 第一次變動、或 dependabot 類 PR 補差額）才跑 `go-mod-download.sh`：整個 workspace 的 `go mod download`，最多 3 次、2／4 秒退避，只重試下載，最後一次的退出碼原樣傳出，log 只寫固定訊息與 exit code，不轉印 proxy 的文字（不用 `gh run rerun` 蓋掉失敗）。
  - **build cache**（GOCACHE）：依「怎麼編譯」分 5 組，`gobuild-<os>-<group>-<ISO 週>`，每組只有一個指定的存檔 job，其餘同組唯讀：`race`＝test matrix 13 個 leg（存檔：`test-apps/rpc`，compile 集合最大）；`check`＝lint、gen-freshness、work-sync、coverage、scripts-test、affected（存檔：lint）；`bin`＝build、k6、k6-auth、k6-wire、console-e2e、console-image、helm（存檔：build）；`kind`＝helm-kind、helm-kind-payment、helm-kind-keda（CGO=0 linux -trimpath；存檔：helm-kind）；`cross`＝release-snapshot（存檔：它自己；release.yml 是 `workflow_run`，只讀同一份）。對照表在 `plan.sh`，沒列的 scope 只有 module cache、沒有 build cache（不會悄悄長出新項目）；helm-kind-target 不編譯任何東西，setup 帶 `go-cache: "false"`（只要 `go` 在 PATH 上給 `MODULES` 用）；`scripts/test.sh` 要求 ci.yml 每個呼叫 setup 的 job 都在表裡，且每組恰好一個存檔者。key 不含 go.sum（依賴變了仍吃得到大部分舊 object），`restore-keys` 只退回同組上一週。
  - **取捨（新鮮度）**：key 是週，當週第一次 main run 存完就是 exact hit，整週不再存，GOCACHE 逐日變舊。實測（run 41938380769 的 `exp-stale` 實驗，apps/rpc、`-race`、`go test -run '^$'` 數 `compile` 次數；先用 K 個 commit 之前的原始碼填 cache，再在 HEAD 量）：K＝0 → 0 次／3–4 秒；K＝25（約 1–2 天）→ 164 次／23 秒；K＝75（約 3.5 天）→ 270 次／29 秒；K＝150（約一週）→ 292 次／31 秒；沒有 cache → 926 次／86–111 秒。所以週末的 cache 仍省下約 68% 的編譯次數、約 65% 的時間，比起剛存好的多付約 28 秒。改成日 key 能把週末的 28 秒壓到約 20 秒內，但每個 main push 日要上傳整組（約 1.3GB），而且舊世代要靠 LRU 或主動刪除退場（沒有 `actions: write` 的刪除 job 時，最多會有 7 個世代並存，超過配額），所以維持週；`plan.sh` 的 `week` 是唯一的旋鈕。
  - **容量**（上限 10GB）：實測冷啟動的 main-like dispatch run（41938380769，逐個 post-step 加總）共存 8 份、2,129MB：module 405、race 306、check 183、bin 146、kind 137、cross 556、tools 102、Playwright 293（舊設計同樣的 run 是 28 份、8,460MB，run 41931769522）。再加 pnpm 約 74MB、golangci-lint 約 10MB。穩態一個世代約 2.2GB；換週當下 5 組 build cache 新舊並存（module、tools、Playwright 不換週）＝ 2×1.33＋0.41＋0.10＋0.29＋0.09 ≈ 3.5GB，離 10GB 還有 6GB 以上，可容納 其他小 cache（見下）。LRU 依最後存取日由舊到新淘汰、7 天沒被存取的也會被移除：上一週的 build cache 在新世代存好後沒人讀，最先退場；當週世代每個 main run 都被讀。保證條件是「2×build＋module＋非 Go＋PR 寫入 ＜ 10GB」，不靠 LRU 運氣；這個式子的左邊目前是 3.5GB＋PR 寫入。
  - **race 組只有一個存檔 leg**：test matrix 13 個 leg 的 compile 集合 95% 以上重疊（冷啟動 870–926 次，pkgs/kernel 135、tools/stripvalidate 174 除外），存檔者是 `test-apps/rpc`（926 次）。其他 leg 在「只有 rpc 的 cache」下還要編譯的 package（同一個實驗，K＝0，每個 leg 從 rpc 的 cache 快照開始）：catalog-rpc 7 次／4 秒、migrate 3／3、payment-rpc 13／5、payment-worker 13／5、worker 7／7、pkgs/catalog 19／6、identity 24／9、inventory 23／9、kernel 2／1、ordering 25／11、payment 38／11、platform 37／14、stripvalidate 2／2（冷啟動各約 66–112 秒）。差額是各 leg 自己的 package，不需要像 module cache 那樣由專用 step 補滿 union。
  - **matrix job**：一個 matrix 的各 leg 若沒有各自的 `cache-scope`，就共用 `github.job`，彼此搶同一個 key（#452 的 k6-auth 三個 leg：一個存成功、兩個 `Unable to reserve`，之後都沒命中自己的 key）。`plan.sh` 因此把每個 scope 對到一組、並且每組恰好一個存檔 scope；test matrix 的 scope 是 `test-<module>`（存檔者 `test-apps/rpc`），其餘 matrix job 的各 leg 共用同一個、非存檔的 scope，只讀。`scripts/test.sh` 檢查：ci.yml 呼叫 setup 的每個 job／module 都對得到組、每組一個存檔者、存檔 scope 不是 matrix job、ci.yml／release.yml 裡每個明確的 `cache-scope` 都是 test 認得的形式。
  - **PR（含 fork、dependabot）**：只讀 default branch 的項目、永遠不存。go.sum 有變時 module cache 退回上一份、只補差額；build cache 不含 go.sum，照吃。fork 的唯讀 token 不會有寫入警告（沒有存檔步驟）。

## gate 腳本不吞外部指令的退出碼（#462）

| `pipeline` | 檔案裡沒有 `set -o pipefail`（或 `set -euo pipefail` 等）卻有 `a \| b` | 管線的退出碼只算最後一段 | 檔頭加 `set -euo pipefail`；被 source 的檔案由呼叫端負責，要在該行寫 exemption |

不必註解的例外只有清理：`kill … \|\| true`、`rm … \|\| true`、`kill … && wait … \|\| true`（行程或檔案已經不在，不是判定），以及 `[ … ] \|\| return 0` 這類條件式守衛。其餘一律要嘛修，要嘛**在同一行**寫豁免註解，並說明為什麼這個指令的狀態不會改變判定：

```bash
out=$(curl -sS "$url" || true)   # exit-ok: empty output is the "not ready" answer; the loop ends in an explicit timeout failure
```

`|| [ $? -eq 1 ]` 只在**賦值**（`n=$(grep -c … || [ $? -eq 1 ])`）有用：`echo "$(… || [ $? -eq 1 ])"`、`expect_eq … "$(…)"` 這種放在引數裡的替換，退出碼到不了 `set -e`，要先賦值再用；沒有 `set -e` 的檔案（`target-test.sh` 等）要自己讀 `$?`。這兩點是 #462 的 fault injection 在 CI 上抓出來的。

**workflow 與 composite action 裡的 `run:`（#465）**：`check-exit-swallow.sh` 也掃 `.github/workflows/*.yml` 和 `.github/actions/*/action.yml`。`scripts/extract-run-blocks.py`（PyYAML；缺少或 YAML 解析不了是 exit 2，不是「乾淨」）把每個 `run:` 抽成一支暫存腳本，套用同一組規則，發現的行號換算回 YAML 的行。**預設 shell 的處理選的是「checker 判斷」，並且順手在每個 workflow 層加 `defaults.run.shell: bash`**：GitHub 對沒寫 `shell:` 的 step 用 `bash -e {0}`，沒有 pipefail，`a | b` 只看 b；`shell: bash` 才是 `-eo pipefail`。checker 依 step `shell:` → job `defaults.run.shell` → workflow `defaults.run.shell` 的順序決定抽出來的腳本帶不帶 pipefail（沒寫 = 不帶，`pipeline` 規則就會擋；`python`、`pwsh` 這類非 shell 的 step 略過），所以有人漏寫 `defaults` 或某個 step 用 `shell: sh -e {0}` 蓋掉它，一樣會紅。`${{ … }}` 換成佔位字，行數不變。`# exit-ok:` 要寫在 `run: |` 區塊的內文裡（單行 `run: cmd # …` 的 `#` 是 YAML 註解，不會進腳本）。workflow／action 檔有任何變動都會跑 scripts-test。診斷類的 step 用 `. scripts/best-effort.sh` 加 `best_effort`。

**`best_effort`**（`scripts/best-effort.sh`，`. scripts/best-effort.sh` 後使用；kind 腳本是 `. "$(dirname "$0")/../../../scripts/best-effort.sh"`）：`best_effort <指令…>` 跑指令，失敗時往 stderr 印 `best-effort command failed (exit N): <指令>` 並回 0——失敗從靜默變成可見。**只給三類**：診斷（失敗報告時多印的 `kubectl get pods`、`diag.sh`）、清理（只限**回收**：wait 已被 kill 的 pid、刪 tmp 檔；後面另有地方判定結果）、wait-gone（`kubectl wait --for=delete`：對象已不在就是想要的狀態）。有 mutant（輸出全部／部分／不輸出後 exit 42，成功、失敗各一格）；checker 的 `besteffort` 規則擋它出現在 `$(…)` 或賦值右邊。要讀輸出或看狀態的呼叫（poll、查找、取值）一律 `rc=0; cmd || rc=$?` 加明確分支（印出哪個呼叫失敗、怎麼處理），不准用 `best_effort`。**還原不是 best effort**：腳本承諾離開時恢復的狀態（helm values、replicas、secret、scale）一律用 `restore_step <指令…>`（失敗印 `restore failed (exit N): …`、記下第一個失敗碼、繼續跑後面的還原）加 EXIT trap 裡的 `restore_exit "$rc"`：進來時 rc 為 0 而還原失敗就以還原的失敗碼離開；進來時 rc 已非零就保留原 rc 並印 `restore also failed`。使用者：`payment-flow.sh`、`payment.sh`、`outage.sh`、`negative.sh`；`scripts/test.sh` 的 restore 區段把各腳本真正的 `restore`／`on_exit` 抽出來，用 stub 讓還原回 42（主流程成功→非零、主流程已失敗→保留原 rc）。`# exit-ok:` 只留給行掃描器誤判且有 mutant 證明的情形，目前 repo 內一處也沒有。

格式是 `# exit-ok: <理由>`，理由至少要有幾個字；空的不算。它是逐行掃描，不是 shell parser：註解行與 heredoc 本文不掃，`pipeline` 只看沒有 pipefail 的檔案，引號裡的 `|` 不算。workflows 與 composite action 的 `run:` 現在會掃（`procsub` 也擋 `done < <(cmd)`，見上），**Taskfile.yml 內嵌的 shell 仍不在掃描範圍**；新寫的 gate 請自己避開（先把輸出放進變數或暫存檔，檢查退出碼，再迴圈）。

**共用 fault-injection helper**：`scripts/fault-inject.sh`，`. scripts/fault-inject.sh` 後用 `inject_fail <dir> <tool> <exit> [<keep>] [<arg-glob>]` 產生 PATH wrapper：先跑真的 `<tool>`，輸出全部（`keep` 省略）、前 `keep` 行或完全不輸出（`0`）之後以 `<exit>` 結束，可用 `arg-glob` 只讓某個子指令（`gh pr checks*`、`go list *`）失敗。gate 的測試對它用到的每個外部指令至少跑「輸出後失敗」與「完全不輸出就失敗」兩格，斷言 gate 非 0，另跑同一個 fixture 的對照組確認是綠的，才知道紅是 wrapper 造成的。`scripts/test.sh` 的 `check-script-modes`、`merge-ready`、`red-stage`、`affected`、`cover-gate` 案例是範例。

## console-e2e 的平行度與 sharding（#447）

基準：run 41920885162，`console-e2e` 一個 job 369s（setup/build/dex ~75s、`task web-e2e` 254s 用 2 workers、ports 24s、payment 19s）。現在它是 3 個 shard 的 matrix（`console-e2e (1)`…`(3)`）：

- **觸發不變**：仍是 `run_console_e2e` 一個旗標、一個 job（matrix 不是新 job），`scripts/ci-changes.sh` 與 `scripts/test.sh` 的規則不動。沒有 branch protection / ruleset 綁舊的 check 名稱。
- **workers**：CI 設 `E2E_WORKERS=4`（ubuntu-latest 在 public repo 是 4 vCPU，實測 `nproc=4`）；本機沒設，`task web-e2e` 還是 Playwright 預設，行為不變。
- **shards**：`task web-e2e -- --shard=i/N`，N 是 matrix 大小（`strategy.job-total`，只有一個來源）。每個 shard 有自己的 runner、postgres service、dex、`bin/worker`，互不共用。
- **覆蓋**：shard 1 先跑 `task web-e2e-shards-check -- N`（`scripts/web-e2e-shards-check.sh`）：每個 shard 的 `--list` 合起來必須剛好等於未分片的 `--list`（每個 test 一次、不多不少，只列不啟 server）。每次 `--list` 都要 exit 0，且它自己的 `Total: K tests` 要等於印出的 test 行數（部分清單加非零退出、被截斷的清單都是紅燈，不是較小的套件）。`scripts/test.sh` 用 stub pnpm 對腳本與真的 `task` 入口各做故障注入：死在一半、完整清單但 exit 42、截斷、漏一個、重複一個、空套件。`web-e2e-ports` 與 `web-e2e-payment` 只在 shard 2 跑（它最輕）。
- **改 shard 數**：改 matrix 的 `shard: [1, 2, 3]`；ports / payment 掛在 `matrix.shard == 2`，要確認該 shard 不會因此變成 critical path。
- **沒做慢 spec**（`history.spec.ts`、`oidc-session.spec.ts` 改 clock／短 interval）：基準 run 41920885162 裡最長的單一 case 是 17.9s，兩個 spec 累計 105s + 84s = 189s；分成 3 shard × 4 workers = 12 個 worker 後，即使這 189s 全部歸零，一個 shard 的牆鐘也只少約 189/12 ≈ 16s（上限估算，不是量測）。其中不少是「over more than two poll periods 沒有再問」的負向等待（`waitForTimeout(4_500)`），縮短等於削弱斷言，不值得。

**量測方法與結論**（數字與 run id 在 PR #453 的描述；這裡只留結論）：

- 探索（單一 workflow run 內的平行 matrix，不是獨立重複，只用來選方案）：workers 2/3/4 是 run 41927472999，shard 2/3 路與 ports + payment 獨立跑是 run 41929103982。結論：4 vCPU 上 workers=4 比預設 2 快約 80–100s 且 0 flaky、0 retry；3 shards 的 `task web-e2e` step 約 50–90s，ports + payment 約 45–50s。
- 定案後的獨立量測是 3 個不同的 workflow run：41934848918（pull_request）、41937591178（workflow_dispatch）、41939558460（workflow_dispatch），同一個 head 9776da2c。三次的 9 個 shard job 全部成功（274 tests = 102+86+86，加 ports 5、payment 2，0 flaky、0 retry）；整個 workflow 的最終狀態不是三次全綠：41934848918 與 41937591178 因 `gen-freshness`（base 問題，#454）失敗，41937591178 另被後續 dispatch 的 concurrency 取消；`task web-e2e` step 最長的 shard 是 87s／86s／80s（基準 254s）。各 shard 的 step 秒數、queue、setup、cache 命中在 PR #453 的描述。比較以 step 秒數為準，job 總秒數受 Actions cache 與 runner 排隊影響，只作參考。
- 多佔並行名額：1 個 job 變 3 個（`console-e2e (1..3)`，多 2 個）。名額飽和、排隊時，多拆 job 不一定讓 wall-clock 變短；排隊另外記，不算在 job 秒數裡。

選 workers=4 × 3 shards；ports + payment 放 shard 2（探索 run 41929103982 裡它的 `task web-e2e` 最輕；加上 ports + payment 後是否仍不超過其他兩片，看 PR #453 的獨立量測）。

## 本機 hook 證據：AgEnD hooks ≠ lefthook（#300）

`git commit` / `git push` 成功，不代表 `lefthook.yml` 的 `gate-fast` / `gate-local` 跑過：git 只執行 active `core.hooksPath` 底下**同名**的 hook。AgEnD 管理的 worktree 會把 `core.hooksPath` 指向 `~/.agend/hooks`，那裡只有 `prepare-commit-msg`、`reference-transaction` 等 AgEnD hooks，沒有 `pre-commit` / `pre-push`，也不呼叫 lefthook。`task tools:hooks` 裝的 lefthook 因此不會被觸發。

### 1. 先驗證 hook 有沒有真的掛上

```bash
git config --show-origin --get core.hooksPath   # 空 = 預設 .git/hooks；有值 = 看來源檔與路徑
ls -l "$(git rev-parse --git-path hooks)"       # 預設路徑
ls -l "$(git config --get core.hooksPath)"      # 有設 hooksPath 時看這個
```

要看到 `pre-commit` / `pre-push` 且內容呼叫 lefthook（`grep -l lefthook <hook>`），才能說 lefthook 掛上。找不到就視為**沒掛上**。AgEnD 的 hooks 與 Claude Code 的 `.claude/settings.json` hooks（`PostToolUse` / `Stop`）也各自獨立，不能互相當證據。

### 2. 沒掛上時：在 exact head 手動跑門檻

在要回報的 commit（`git rev-parse HEAD`）上跑 `task gate-local`（commit 前的檔案檢查用 `task gate-fast FILE=…`），回報要留命令、exit code 與輸出摘要。措辭固定：

| 情況 | 可以寫 | 不可以寫 |
|---|---|---|
| lefthook 掛上，hook 跑過（有 hook 輸出） | lefthook 通過 | — |
| 沒掛上，手動跑 gate 且 exit 0 | **手動 gate 通過，hook 未執行**（附 head SHA、命令、exit code） | lefthook 通過、hooks 通過 |
| 沒掛上，沒跑 gate | 本機 gate 未執行 | 任何「通過」 |

範例：

```text
head: 0b95a126…（git rev-parse HEAD）
core.hooksPath: /Users/sean/.agend/hooks（file:…/.git/config）；hooks 目錄無 pre-commit / pre-push
$ task gate-local → exit 0（check-gen-fresh 乾淨、buf lint 乾淨、affected modules go test -race ok）
結論：手動 gate 通過，hook 未執行
```

### 3. 每個 head 各自驗證

merge commit、rebase 後或任何新 head 都要在**該 head** 重驗，不沿用 parent 的結果。回報裡的 SHA 要與最後 push 的 head 一致。

### 4. 已由 exact-head CI 證明的不必重跑

CI 在 `refs/pull/N/merge` 上跑（見 `task merge-ready`），綠燈對得上目前 head 時，下列門檻不必本機重複：gen-freshness（含 TS）、`task lint`、work-sync、`go test -race`（test matrix）、coverage、build、helm、k6 / k6-auth / k6-wire / helm-kind / helm-kind-payment / helm-kind-keda / helm-kind-target、release-snapshot、web。哪些 job 實際執行取決於改動路徑（`scripts/ci-changes.sh`）；被跳過的 job 不是證據。本機手動 gate 的價值在於「push 前就知道」，**不取代** CI；CI 也無法證明本機 hook 曾經執行。

### 5. 不要繞過 hook

不用 `-c core.hooksPath=/dev/null`、`--no-verify` 跳過 hook，除非 lead 明確授權；授權時要在回報裡寫明被跳過的 commit 與理由。也不要為了讓 lefthook 跑起來去改全域 `core.hooksPath` 或 `~/.agend/hooks`（影響其他 worktree 與 daemon 保護）；缺 hook 就走第 2 點手動跑。

### Claude-Session trailer

repo 沒有這個規範：`CLAUDE.md`、`docs/`、`.github/`、`scripts/` 都沒有 `Claude-Session`，近 60 筆 commit 也沒有；commit 規則只有 Conventional Commits。#297 提到的 trailer 來自當次派工 brief，不是 repo 要求。AgEnD 的 `prepare-commit-msg` 注入的是 `Agend-*` 與選用的 `Signed-off-by`，且 hook 失敗不擋 commit。
